# TranscriberPrototype — Project Documentation

*Last updated: 2026-08-29 (five faults in one recording — D-035)*

## Purpose

TranscriberPrototype is the **Live Seminar Transcriber**: a single-user local application that
continuously captures audio from a microphone or from system playback, transcribes it in near-real-time
through a pluggable speech model, maintains a growing timestamped transcript, and exposes that
transcript to a language model so the user can ask questions about a talk while it is happening.

The driving use case is attending a seminar or colloquium on an unfamiliar topic — asking, mid-talk,
*"Summarise the last ten minutes,"* or *"What does the speaker mean by that term?"*

A Python backend owns the entire pipeline and publishes an HTTP plus WebSocket contract. The frontend
is server-rendered from the same process: Jinja2 templates, plain CSS, and vanilla ES modules, with no
build step.

## Architecture Overview

Detail in [architecture.md](architecture.md).

```text
microphone / loopback / WAV file
    ▼  audio capture — 16 kHz mono float32, ring-buffered, never blocking
    ▼  voice activity detection — speech flag, hysteresis, pause events
    ▼  streaming engine ◄──► ASR abstraction  (SEAM A: mock, faster-whisper)
    ▼  transcript store — SQLite, append-only, written through on commit
    ├──────────────► transport — WebSocket events ──► browser
    ├──────────────► polish pass — a minute at a time, rewritten for reading ──► browser
    ▼  context pipeline — rolling summaries, glossary, chunk index
    ▼  chat orchestrator ◄──► LLM abstraction  (SEAM B: local, hosted API)
    └──────────────► transport ──► browser
```

The design rests on two swap points. **Seam A** lets the speech model change without touching the
commit logic; **Seam B** lets the language model move between a local server and a hosted API. Both
are narrow interfaces defined early because everything else is replaceable later and these are not.

| D-004 | **FastAPI confirmed** for the backend | Async-native, which suits a continuous WebSocket event stream alongside ordinary request/response; generates the OpenAPI spec `web/shared/contracts/` needs. The assumption recorded at initialization is now a commitment. |
| D-005 | ~~React + Vite + TypeScript assumed for the frontend~~ | **Reversed by D-011.** |
| D-006 | Only `repository-structure` and `planner` skills adopted | The user selected these two; the others did not exist in this repository. |

| D-009 | Initializer files deleted after migration | Content migrated into `docs/skills/`; nothing lost. |
| **D-010** | **The product is a live streaming transcriber, not an upload-and-poll job service** | The two design documents specify continuous capture with a persistent event stream. The upload/job model recorded at initialization describes a different application: it has no notion of a live hypothesis tail, a commit policy, or health telemetry, all of which are central here. Keeping both would have meant two contradictory contracts. `architecture.md`, `routes.md`, `api-contract.md`, and `data-flow.md` were rewritten rather than extended. |
| **D-011** | **Frontend is Jinja2 templates + vanilla ES modules + plain CSS, no build step. Reverses D-005.** | The user asked for a heavily compartmentalised template/CSS/JS structure rather than a single file, and for HTML and JavaScript to be the primary artifacts. Server-side includes give that compartmentalisation directly; a framework would add a build step, a lockfile, and a toolchain for a UI that is two panes and a settings modal. It also removes the npm/Node requirement entirely — one runtime, one package manager. The HTTP/WebSocket contract is unchanged, so a framework rewrite later remains possible without touching the backend. |
| **D-012** | **ASR ships as a scripted mock plus a real-time WAV file source.** ~~`faster-whisper` lives behind an optional dependency group.~~ | The architecture is explicit that development should happen against recorded audio because live microphone input is not reproducible, and that the commit policy needs a mock backend with scripted outputs to be testable at all. **Both halves still hold; only the packaging changed.** The mock and the file source remain, and the test suite still runs against them. The optional-group half is **reversed by D-023.** |
| **D-013** | **HTTP for operations, WebSocket for the live stream** | The transcript is a continuous server-to-client push; everything else is ordinary request/response. Polling a transcript that updates once a second is wasteful and adds latency to the one thing that must feel live. The socket is treated as disposable — reconnection replays from the last segment id, which removes an entire class of bug. |
| **D-014** | **One OpenAI-compatible HTTP client plus a native Anthropic client** | Ollama, llama.cpp's server, LM Studio, vLLM, LocalAI, and OpenAI itself all expose the same chat-completions shape, differing only in base URL. That collapses an apparent provider matrix into two implementations. Anthropic's request/response shape genuinely differs and gets its own client. |
| **D-015** | **SQLite with FTS5 for persistence** | Survives a crash mid-talk, gives full-text search over the transcript for free, and needs no server. A 90-minute session held only in memory is unrecoverable if the process dies at minute 80. |
| **D-016** | **No authentication; bound to `127.0.0.1`** | Single-user local application, so an auth model would be ceremony with no security benefit. The binding is the actual control: an unauthenticated transcript endpoint on a network interface would publish the contents of a private room. Recorded as a decision so it is not mistaken for an oversight. |
| **D-017** | **Credentials go to the OS credential store, never a config file** | Keys in a plaintext config file get committed, backed up, and shared by accident. `keyring` maps to the correct store on every platform; an environment variable is the documented fallback. The frontend is only ever told whether a credential is *present*. |
| **D-018** | **The transcript is polished a minute at a time, and polishing is not summarising** | A speech model emits fragments: two seconds of speech with guessed punctuation, and a page of those is a wall of half-sentences. The clean-up pass rewrites each finished minute into readable prose. Three properties make it safe. **It is not summarisation** — `services/context/` already summarises, which is lossy by design; this must not drop a claim, so the prompt is a numbered instruction list rather than a request, and a length guard rejects a rewrite that came back as a summary. **It is additive** — polished blocks are stored alongside the segments they cover, never in place of them, so the verbatim record, its timestamps, search, and export are untouched and a bad rewrite costs one redundant row. **Its fallback is doing nothing** — with no language model, an unreachable one, a failed call, or a result that fails the guard, no block is produced and the page shows exactly what it showed before the feature existed. Chunks are cut at a pause in speech rather than on a timer, and always at the end of a committed segment, so no chunk ever contains half a sentence or omits words still in the hypothesis tail. **Amended 2026-08-15**, when what the pass produced turned out to be wrong in three ways. It transcribed dictation literally, so a speaker saying "guard dot py" appeared on the page as *guard dot py*; the prompt now writes such references out and is granted exactly enough licence to repair the grammar around a substitution, since a written form is a different number of words from a spoken one. It carried no timestamps, so a polished stretch could not be traced back to when it was said; markers are now placed deterministically *before* the model sees the text and reconciled against that list afterwards, because a model asked to work out timestamps fabricates plausible ones and a fabricated timestamp is worse than none. And it broke to a new line constantly; the chunk is now handed over as one continuous run, one continuous paragraph is what should come back, and the page draws consecutive minutes as consecutive paragraphs with no rule or heading between them. |
| **D-019** | **Invented speech is filtered on the model's own confidence, not on heuristics alone** | Whisper does not go quiet on non-speech audio: it returns the phrases its training data ends with — "thank you", "bye", a bare "you" — confidently and with plausible word timings, and they are indistinguishable from a transcript by reading them. Reported from real use and reproduced on a synthetic tone fixture that produced a segment saying "you". The existing silence gate was working; its *input* was the problem, because an energy detector is cleared by a fan or a keyboard. The fix uses what the model already knew and was discarding: `no_speech_prob` and `avg_logprob` were computed on every pass and never read, because the backend collected `segment.words` and nothing else. Four layers now: the decoder's own Silero filter keeps non-speech out of inference (measured *faster*, not slower — less audio to decode); the model's no-speech estimate condemns a pass, with a second tier above 0.85 where it needs no corroboration; optional word-confidence; and a literal list of the observed boilerplate phrases, matched only when one is the entire output of a short pass. **The governing constraint is that every layer can delete something real**, so defaults are conservative, each layer switches off on its own, discarded text is logged, and the count is published and surfaced in the status bar once non-zero — a filter that silently removes speech is a worse bug than the one it fixes. Absent signals are read as *no opinion* rather than as grounds to drop. |

| **D-020** | **Capture mode and run state are separate vocabularies with separate controls, defined once and mirrored** | The application is growing from one thing it can do to three, and a boolean cannot hold that. Two questions are being asked at once — *what kind of recording is this* and *where has this recording got to* — and the tempting answer, one control that cycles through everything, fails on inspection: a button whose meaning depends on how many times it has already been pressed cannot be understood without reading its label, and the label is the thing that changes. So there are two controls, sitting adjacent so they still read as a pair. The **run states are six, not two**: `arming` exists because window capture must collect options and wait for a desktop picker before anything is captured, and `processing` exists because a recorded pass transcribes after capture ends and can run longer than the recording did — both are states a user will sit and look at, so both need a name, a label, and an announcement rather than being folded into "recording". Which states each mode can reach is data (`MODE_STATES`), not branching, because `live` never processes and only `window` arms, and encoding that as conditionals spread across the interface is how a mode ends up displaying a state it can never be in. **The vocabulary is defined twice on purpose and defended by a test.** It has to exist in Python, which owns the session, and in the browser, which draws it; D-011 removed the build step that would otherwise let one import the other. Two hand-maintained copies drift, and they drift silently — a mode renamed on one side leaves the other sending a string nobody handles, and the interface shows a confidently wrong state rather than an error. `tests/utils/test_mode_vocabulary.py` therefore reads `modes.js` as text and asserts every name, list order, and mode→state edge matches. Parsing it with a regular expression rather than a JavaScript engine keeps the suite free of the Node toolchain D-011 deleted, at the cost of that one file staying simple enough to read that way — a trade its own header states so the next editor knows the constraint is deliberate. |

| **D-021** | **A recorded session does no inference while capturing, and its post-capture pass deliberately bypasses the commit policy** | Live transcription commits two to four seconds behind the speaker because it must decide what is settled while more audio is still arriving. That latency is the price of watching words appear, and when nobody is watching it buys nothing at all — while the inference itself still costs a CPU running flat out for the length of a talk. `recorded` mode inverts the trade: capture writes a WAV and starts no engine, and the whole file is transcribed once, afterwards, with every word of context available. **LocalAgreement is not reused for that pass**, which is the decision most likely to be second-guessed. Agreement answers one question — *what is safe to show now, given the next second might change it?* — and once the file is complete that question no longer exists. Running it anyway would reproduce its latency and its trimming heuristics for nothing and would throw away the context that makes the mode worth having. The **segmenter** *is* reused, and that is what makes the mode cheap to integrate: identical segment shape, id sequence, and boundaries, so the store, the FTS index, export, citations, and the polish pass all work on a recorded transcript without knowing how it was produced. Three consequences are load-bearing. **The sink writes on the capture thread rather than through the drop-oldest queue** — that queue exists to protect inference latency by discarding audio, and audio discarded from a recording is a hole in the only copy of the talk; a buffered kilobyte write is orders of magnitude cheaper than the pass the queue decouples from, so the constraint it guards is not reintroduced. **The pass outlives the session it came from**, so the transcript store is *handed over* rather than borrowed and the runner alone closes it — two owners of one SQLite connection, one tearing down while the other writes, was not hypothetical: it happened, because ownership was a parameter to teardown and `shutdown` reaches teardown by a second path that could not know. **Audio is deleted only once the transcript is safely written, and kept whatever the retention setting says when a pass fails** — at that moment it is the only remaining copy of what was said, and the failure message names its path because `/api/recordings` can run the pass again against it. |

| **D-023** | **Every capability is an ordinary dependency. There are no optional groups.** | `uv run app.py` is the whole install and the whole run. The five things that used to be extras — real transcription, device capture, the Silero detector, the credential store, and the D-Bus client — are now plain dependencies, so nothing the application can do requires a second command to unlock. **This reverses the packaging half of D-012**, whose reasoning was that keeping the speech model optional made `uv sync` fast and kept model downloads out of the test suite. Both were true and neither survived the actual trade: a user who presses record and is told to go and run `uv sync --extra asr-whisper` has had a worse first five minutes than a slower first install would have cost them, and it is a failure they hit *at the moment they wanted the tool*, which is the worst possible time. The second reason turned out not to be a reason at all — **the weights were never in the wheel.** `faster-whisper` downloads them on first load, so `uv sync` never fetched them and the test suite was never at risk from installing the package; only from *loading a model*, which the mock backend still avoids. Measured after the change: a warm `uv sync` takes under a second and the virtualenv is 477 MB, which is the honest cost and is paid once. Two things remain outside `uv` and are documented rather than hidden: GStreamer and a desktop screen-sharing portal are system packages, and `docs/workflow.md` names them. The consequence for diagnostics is that `GET /api/health` and the startup banner change meaning — a capability reported missing now indicates a **broken install**, not a choice, so every message that used to say "install the extra" says "reinstall with `uv sync`". |

| **D-022** | **Window capture is a negotiated portal stream, driven through GStreamer, and its video is the expendable half** | Three facts about this machine decided the whole shape, and all three were established by inspection rather than assumed. **It runs Wayland**, where an application cannot enumerate windows, cannot read another window's pixels, and cannot grab the screen — so `org.freedesktop.portal.ScreenCast` is not a choice among options, it is the only route. The compositor shows *its own* picker; we never learn what windows exist, which is why nothing in the interface may imply a list, a grid, or a pre-selection, and why there is a dialog in the middle of the feature that can be declined. **This ffmpeg has no `pipewiregrab`** while GStreamer's `pipewiresrc` is present, so capture runs through `gst-launch-1.0` as a subprocess — which also keeps PyGObject and its system introspection out of the `uv` virtualenv, the same reasoning D-011 applied to the frontend. ffmpeg is still used for the one job it can do here: remuxing two finished files. **There is no hardware encoder** — `x264enc` and every VAAPI element are absent — so video is software VP8 competing with the speech model for the same cores, which is why the defaults are 720p at 15 fps and why the encoder is tuned for not falling behind rather than for file size. Three design consequences follow. **The video is expendable and the audio is not**: an unavailable machine, a portal error, a dead recorder, or a window closed mid-talk each end the video and none ends the session, because a transcript cannot be recreated and a video of a window can — the sole exception being the user *declining*, which ends the run, since starting an audio recording they did not ask for reads a refusal as a yes. **Two transcripts are kept, not one**: a window session that transcribed live and again afterwards stores the second as a separate revision, because the live one is what the user watched and what any chat citation points into. **Kept, and shown one at a time** — the reported fault of a finished result that carried the talk and then the talk again was every reader merging the two: the second pass publishes its segments over the same socket the browser is using for the first, and three read paths served the union of both. One pass is now what is displayed and exported, with the Live/Final switch as the only way to the other. **The preview is pulled as an image, never pushed over the socket**, whose backpressure policy makes transcript events undroppable — video sharing that channel is the one thing that could delay a committed segment. Audio is *the machine's*, not the window's: the portal carries video only, and the pre-flight sheet says so in text, because a user who assumes otherwise discovers it after the talk. |

| **D-024** | **The desktop presence is a second, deliberately thin process — a remote control, not a rewrite** | A page in a browser tab cannot register a system-wide hotkey, cannot place an icon in the tray, and does not exist when no browser is running. Everything Plan 5 asks for is therefore outside the web application by construction, and the question was only how far outside. The answer is **as little as possible**: a companion that owns exactly two things — the tray icon and the shortcut registrations — and talks to the server over the same loopback HTTP the browser uses. It **polls** rather than consuming the WebSocket, which keeps it stateless and disposable: it can be killed and restarted at any moment without the server noticing, and that property is what makes a background helper safe to ship at all. A second socket consumer would need reconnection logic, replay handling, and a view of transcript events it has no use for. Keeping it this thin is what stops this becoming the desktop-application rewrite `docs/checklist.md` still lists as an open, unmade decision. **Shortcuts go through the desktop's own service** (`org.kde.KGlobalAccel`), not through input devices. Under Wayland an application cannot grab keys at all, and reading `/dev/input` would mean a keylogger running as the user — never acceptable for a tool whose entire purpose is recording private rooms. The consequence is that shortcuts are revocable from System Settings, which is the correct place for them, and that a desktop without such a service gets a report naming the command to bind by hand rather than silence. **The security posture, stated plainly rather than left to be inferred:** the toggle endpoint is unauthenticated and loopback-bound under D-016, so anything running as this user can start a recording — the same was already true of `/api/session/start`, and the companion widens the *convenience*, not the exposure. Autostart writes one systemd user unit and removing it is one documented command. The tray reads the desktop's shortcut service rather than a marker file we wrote, because a stale marker would tell the settings panel the keys work when the process behind them has gone. |

| **D-025** | **The launcher repairs its own GPU build, because launching is what breaks it** | On an AMD machine `faster-whisper` needs the ROCm build of CTranslate2, which is a GitHub release asset rather than the PyPI wheel `pyproject.toml` resolves to. `uv run app.py` synchronises the environment against the lockfile *before any of this repository's code executes*, so **the command that starts the application is the command that removes its GPU support** — not once, but on every single launch. This was diagnosed the slow way: the wheel was installed by hand, verified working, and found broken again at the next start, which reads as a mysterious regression rather than as the launcher doing exactly what it was told. Documentation cannot fix a fault whose trigger is the documented start command, so `app.py` restores the kept wheel from `data/wheels/` itself and prints one line saying it did. **It is narrow on purpose**: it fires only when the machine has an AMD GPU, a wheel matching the installed CTranslate2 *and* this interpreter is on disk, and the installed build did not come from that wheel. That last check is what makes it safe to run every time — a wheel installed from a file records its origin in `direct_url.json` and one from an index does not, so the test is a single small file read and the condition is false immediately after a successful repair, which is why it cannot loop. `TRANSCRIBER_NO_GPU_REPAIR=1` turns it off for anyone who wants the environment left exactly as the lockfile describes it. **A second fault was hiding behind the first.** CTranslate2 drives ROCm through the CUDA API, so the load error on an AMD machine says *CUDA* — and the message repeated that back, telling the owner of a Radeon to check an NVIDIA driver and a cuDNN install that will never exist on that machine. The message now consults the acceleration report, which knows what hardware is actually present, and names the real remedy. The alternative considered and rejected was pinning `[tool.uv.sources]` at the local wheel: it would fix this machine and break every other one, since the path, the interpreter tag, and the architecture are all baked into a file uv insists must exist. |

| **D-026** | **A capture is verified by opening the file it produced, and nothing is asked to work out a size** | Window recording shipped with 1291 tests passing and did not work in any respect a user could see. Every capture test asserted the *shape of the launch line*; not one opened the file. So a well-formed pipeline that wrote **480x16** — a sixteen-pixel-tall strip of a talk — passed, because `gst-launch-1.0` exited zero and nothing about the command was invalid. `tests/transcription/test_capture_output.py` now runs the real pipeline and reads the result back, substituting only `pipewiresrc`, which is the one element needing a compositor. It checks dimensions, frame count, and **mean luminance** — the last because a correctly-sized all-black recording is what a dead or wrong PipeWire node produces and nothing else detects it. These tests are slower than the rest of the suite; that is the price of checking the thing itself, and this row exists so that a contributor who finds a slow test and not its purpose does not delete it. **The design consequence is that the pipeline states sizes rather than negotiating them.** Fixation failed twice: quietly, resolving a caps *range* against a preview's width to produce the 480x16 strip; then loudly, overflowing outright — `assertion 'denom > 0' failed`, a 480x32767 JPEG, `pipeline doesn't want to preroll` — because the portal on this desktop reports **no stream size** and `pipewiresrc` does not always present fixed caps, so the scaler was computing against a pixel-aspect-ratio it could not use. Reproduced with `pixel-aspect-ratio=1/2147483647`. Now the preview names two concrete numbers and letterboxes, and the recording branch carries **no scaler at all** unless both source dimensions are known and exceed the ceiling. Recording at native size costs encoder time on a machine with no hardware encoder, and that is the right trade: a larger file that plays beats a smaller one that does not exist. **Two further faults shared the same character — well-formed code, invisible failure.** `start` guarded on `is_running`, which cannot become true until the audio source is open, several awaits and a model load later; every start request arriving in that window passed the guard and, in `window` mode, opened its own portal dialog. The session is now claimed synchronously before the first await. And the *test suite itself* was opening the compositor's picker five times a run and blocking 120 seconds on each, because `tests/api/test_session_modes.py` starts a window session through the real route; `PortalSession._connect` turns every transport failure into `PortalUnavailable` by design, which is why an earlier attempt to catch this by making the connection raise reported no offenders. `tests/conftest.py` now keeps every test away from the portal, suite-wide. **On timestamps:** stored times were *measured* before anything was changed — a recording that says what time it is, one tone per second — and found correct at both revisions, so the fix went where the fault actually was: the prompt, and dropping any cited moment that matches no line the model was shown. A wrong timestamp shown confidently is worse than none. **Window audio is part of the same repair.** The portal carries video only, so a window's sound was always a separate capture — and that capture was the *microphone*, so recording a talk also recorded the person watching it. PortAudio cannot reach the alternative: this machine lists fifteen inputs through `sounddevice` and none is the `.monitor` of a sink, and the `loopback` kind the device list reports is a name heuristic that labels an HDMI *output* as a loopback. Window mode therefore captures the default sink's monitor through `pw-record`, resolved at start time because the default sink changes when a dock or a headset appears. One flag is load-bearing: without `--container=raw`, `pw-record` writes an AU header to stdout whose bytes decode to **NaN**, and a single NaN propagates through every downstream mean, peak and RMS — a capture that runs at the right rate for the right duration and transcribes silence. |

| **D-027** | **Capture is hardware-encoded, caps-driven, and measured on every recording** | Four findings, in descending order of what they cost. **(1) There was a hardware encoder all along.** The machine was believed to have none, which is why video was software VP8 at 15 fps competing with the speech model for cores. `gst-inspect-1.0 va` registers `vaav1enc` — the `va` plugin only registers an encoder when the driver advertises the entrypoint, so that listing *is* the capability test. Measured through the real pipeline on 150 frames at 720p: **1.25 s of user CPU for `vp8enc` against 0.30 s**. AV1 rather than H.264 by necessity: Fedora strips the H.264 and HEVC VA-API entry points from its Mesa build for patent reasons, so `vah264enc` never registers on a stock install even though this hardware supports it; AV1 is royalty-free and present. Selection is by probing, so a machine without the entrypoint falls through to software with no branching. **(2) The portal's `size` was the wrong question.** It is optional *and* specified in compositor logical coordinates, explicitly not pixels and explicitly permitted to differ from the stream's own size — so on any scaled display it is the wrong number even where present. Geometry is bounds-checked, computed in floating point, rounded to even, and idempotent; even rounding stops being luck the moment the encoder is a hardware one. **(3) A window's audio can be captured without stealing it.** PipeWire allows a node's output ports to be linked to more than one destination, so the application's stream is tapped *additively* into a private sink and keeps playing to the user's speakers — verified against the real graph before implementation, and asserted on every test run by checking the original link survives. `pactl move-sink-input` is **not implemented at any priority or behind any flag**: it is the only approach that can leave someone unable to hear what they are recording. Which stream belongs to a window is *ranked, never decided* — PipeWire's own docs warn that only `pipewire.*` properties identify an application safely, and the one trustworthy PID resolves to `pipewire-pulse` for nearly everything on a desktop. **(4) An empty transcript now explains itself.** `done_no_speech` is a terminal state distinct from `done`, and every recording carries a measured sidecar — RMS, peak, clipping, band energy, dominant frequency — because "322 seconds processed, 2 segments" is what a broken transcriber and an accurate one both look like. **The discipline underneath all four:** assertions moved into the running recorder, where they see what the machine produced rather than what the code intended. That is also how a mistake in this very change was caught — a leaky queue added on the research's suggestion dropped 150 frames to nine, and the existing frame-count assertion passed it at 12 of 20. |

| **D-028** | **A shared name is a shared resource, and an unnamed default is a decision somebody else made** | Two faults, unrelated in mechanism and identical in character: both were invisible, both survived a green suite, and neither was in the code that appeared to be responsible. **(1) Recordings came back as bit-exact digital silence** — `rms: 0.0, peak: 0.0` in the sidecars, not quiet audio but literal zeros — while older ones from the same code contained sound. The capture logic was correct. The tap's null sink was called `transcriber-tap`, a constant; `pactl load-module` outlives the process that called it, so every session ending without teardown left one loaded, and **PipeWire does not uniquify node names**. With several present, `pw-link <app>:output_FL transcriber-tap:playback_FL` and `pw-record --target=transcriber-tap` resolve that name *independently and can resolve it to different nodes*, so the recorder captures a sink nothing is linked into. Measured, same code one minute apart: RMS **0.0** with five leaked sinks present, **0.0058** once they were unloaded. **The leak was the test suite.** `_open_application_tap` was never stubbed, so any test opening a window session's audio loaded a real null sink into the developer's live PipeWire graph and never closed it — three per run from five tests. The suite that reported the feature green was manufacturing the state that broke it. Sinks are now named `transcriber-tap-<pid>-<hex>` so collision is impossible, stale ones from dead processes are swept at open, and `tests/conftest.py` keeps the suite out of the graph entirely — the same guard, and the same lesson, as the portal dialogs one plan earlier. A related guard could not fire: `link` tested `if _run(...) is not None` and `_run` returns `""` on failure, so every link counted as a success. **The general form: any check whose failure mode is "records nothing" must be asked a question it can answer wrongly.** `carries_audio` now listens to the tap for 600 ms before the session commits — real audio, even a silent room, never produces a run of samples whose every byte is zero — and only when a linked node reports `running`, because a paused video is the user's business and not a fault. **(2) The video was "extremely compressed", and nothing had chosen how compressed.** `vp8enc` ran with no rate control named, leaving `target-bitrate` at its factory default of **256 kbps**; recordings measured 345–357 kbps at 1080x1064. A bitrate cannot be substituted because the portal reports no stream size (D-026), so the pipeline does not know the resolution to compute one from, and `bits-per-pixel` — the property that exists for exactly that — has no effect in this build. Constant quality with a bitrate *ceiling* needs no resolution: one setting measured 4909 kbps at 1080x1064 and 1038 kbps at 640x360. Fifteen seconds of real capture: **487 kbps / 35.44 dB before, 2161 kbps / 44.80 dB after**, for 2.78 s of CPU against 1.86 s — a five-times realtime budget, so the encoder still leaves cores for the model. Two latent faults surfaced beside it: `openh264enc ! matroskamux` does not link without `h264parse`, and the NV12 capsfilter was keyed off "has a parser" as a stand-in for "is hardware", which `openh264enc` — I420 only — would have broken. Neither had ever run on this machine, because this machine picks `vp8enc`. |

| **D-029** | **A check is only worth what it has been measured against** | Four faults reported together, unrelated in mechanism and sharing one shape: each was a piece of code that *looked* right and had never been exercised against the thing it claimed to govern. **(1) Two system messages.** `context/assembler` sent standing instructions and context blocks as separate `system` messages — legal in the OpenAI schema, refused by real servers, so **every** question returned `400 System message must be at the beginning` whenever any context block survived the budget. No unit test on a message list could catch it, because the shape is only wrong at a server; the guard is now a live test that sends a fully assembled question to a real endpoint, verified to fail with the user's exact error when reverted. **(2) A probe whose premise held for the wrong device.** The tap verification added a day earlier treated a run of bit-exact zeros as proof the graph was not delivering. True of a microphone, which always carries a noise floor; **false of an application**, which writes literal zeros between sounds, while paused with the stream open, or through a silent lead-in — so working recordings were refused for being quiet. Timing was measured first and cleared: with a tone playing the probe passed at every window down to 0.1 s. The window was never the problem, the *question* was. It now counts live links in the graph, which cannot be confused with whether anything is audible, caught in the act against the real daemon: `live_links=2` versus `carries_audio=False` on the same tap in the same second. Two further faults surfaced in that path while measuring — `match` was documented and never used, so "record this window's audio" recorded the machine's; and the tap linked once at open despite `tap.py`'s own docstring saying the set must be watched, so pressing record and *then* play recorded nothing. **(3) A guard that discarded what it had never heard.** The silence gate committed the previous pass's hypothesis and then threw the whole buffer away, losing every second recorded since — 23 consecutive words across one ordinary pause, and the same hole in `flush` at the end of a run. The user's log named `commit-timeout` because that is the guard that logs; the words went missing elsewhere, which is why the losslessness harness was written *first* and allowed to contradict the plan. The rule it settled on: **no audio may be discarded without having been transcribed at least once** — audio heard and found empty is not audio lost. Fixing it naively then produced a worse fault the existing suite caught immediately, hallucinated speech over silence (D-019), and gating on the VAD could not resolve it because half the requirement is transcribing speech the detector *misjudged*. Neither opinion decides it; the buffer's own level does, at −46 dBFS. **(4) The enclosing element was not the unit assumed.** Copied timestamps read `00:00:00` because `_startOf` returns the enclosing `data-start`, and for polished prose that is a **block** — measured at six blocks across 784 seconds and two across 300, the first of each starting at 0.0 and running past two minutes. The inline `[mm:ss]` markers already in the prose carry the real answer. **The through-line:** in all four the code was self-consistent and the suite was green. What separated them from working code was a measurement nobody had taken — against a real server, a real application's audio, real speech through the guards, and a real block's duration. |

| **D-030** | **A link that exists is not a link that carries** | Reported: window recording "not working again" — the video recorded perfectly and the transcript stayed empty. The tap was built exactly as designed and delivered **bit-exact digital silence**: the null sink created, the browser's ports linked, every link reading `active`, both nodes reading `running`, every gain — `volume`, `channelVolumes`, `softVolumes`, monitor and mute alike — reading 1.0, and 43 seconds of capture at precisely the right sample rate containing not one non-zero sample. **Neither existing guard could see it.** `live_links` counts links and there were two of them; the silence probe it replaced (D-029) was removed for the sound reason that bit-exact zeros are also what a paused video looks like. The mechanism itself is not broken: a native client (`pw-play`) linked into the *identical* tap in the same second came back at **440.4 Hz, RMS 0.35**, while the browser through the same tap stayed at 0.000000 — measured four times alternating, and again against a null sink created with the browser's own rate and channel layout. What separates them is `client.api`: LibreWolf's playback nodes are `pipewire-pulse` clients, and on PipeWire 1.6.8 their output does not reach an additive second sink. **The third question resolves what neither could alone.** The tap's silence and the machine's own output are now probed together, and only the combination *tap silent **and** speakers audible* means a dead tap — a pairing a paused video cannot produce, since it silences both. On that verdict the capture widens to the machine's whole output rather than refusing, because a wider recording still contains what the user asked for and an empty one contains nothing; the cost, that every other sound lands in the transcript, is said out loud rather than absorbed. `-1.0` is carried as *unknown* and distinguished from silence throughout: a probe that could not run must never be what changes a recording. Two supporting findings, both measured: the fallback target must stay the `stream.capture.sink` form, because `<name>.monitor` on a null sink **silently records the microphone** — which read RMS 0.065 whether or not anything was linked, indistinguishable from real capture by level alone because the microphone hears the speakers; and `node.dont-fallback` is unusable on this version, rejecting valid targets by name and by id alike. Separately, `link` keyed its work by `node.name`, and a browser gives every tab's node the same one — so the second tab's ports were marked already-linked and skipped, and exactly one tab was ever captured. It links by port object id and keys by node id now. |
| **D-031** | **A finished transcript stays readable, because the question people ask most comes after the talk** | Reported: after stopping a transcription, *"Summarise the last 10 minutes"* answered **"There is no transcript to ask about yet"** while the finished transcript was plainly on screen. Both halves of that were true at once, which is what made it baffling to look at: the pane's transcript is the **client's** copy, accumulated over the WebSocket while the session ran, and it outlives the store the server reads from. `_teardown` closed that store and set it to `None`, and everything that reads a transcript reads it through `SessionManager.store` — the assistant's `store_provider`, both readers in `routes/transcript.py`, and the stats in `state()`. **One line, three faults, and only the first was reported.** A reload showed an empty transcript because `state()` read `_store` directly and had no stats to re-fetch from — carried in the checklist as its own open item since the multi-mode expansion, with this exact remedy proposed. And `session_seconds` read `_store` directly too, returning `0.0` at precisely the moment its own docstring promises a fallback *"so a question asked after a session ends is still positioned correctly"* — which would have made *"the last ten minutes"* resolve to the range `[0, 0]` and select nothing **even once the store was retained**. A second fault sitting directly behind the first, invisible until the first was fixed, and the reason a repair that stopped at "retain the store" would have looked wrong for a different reason. The store is now held open for reading until the next session starts: one SQLite connection, kept exactly as long as the answer is still the one anyone wants, released on the next start and on shutdown. The two modes that run a batch pass need their own path — `recorded` and `window` hand ownership to `TranscriptionRunner`, which closes the store itself — so release reopens it from its path, the same call `routes/sessions.py` makes for any past session. **Nothing about the assistant, the quick actions, or the context assembler changed**, and that is the point: they were already correct and were being handed `None`, so fixing them would have been a workaround for a fault one layer down. The honest empty case survives — an application that has never recorded still says there is no transcript to ask about, held there by two tests, because retention must not turn a true refusal into an invented answer. |

| **D-032** | **A recording is a directory, not a scatter of files sharing a prefix** | `data/recordings/` held every artefact from every session in one flat list — audio, video, preview frame, muxed copy, measurement sidecar — each name prefixed with the session's stamp. After a fortnight of use that is several hundred files from several dozen recordings, interleaved by name, and answering "what came out of the recording I made on Tuesday" means reading filenames. Each recording now owns a directory named `<YYYYMMDD-HHMMSS>-<session-id>` with fixed names inside it. **The directory name is deliberately the transcript database's stem.** The transcript stays in `data/sessions/` and is *not* moved: it is an open SQLite file for the whole of a session, and relocating one mid-write to tidy a listing is a bad trade. Sharing the name joins them without moving anything, which is what makes "does this session have a video" one directory listing rather than a filename search — and it is what the media indicators (D-033) and the export (D-034) are both built on. Files written before the layout existed are grouped into it once at start-up, by the key their names already carry; nothing is deleted, nothing is overwritten, and a name that does not parse is left where it is, because a recordings directory is a user directory and a migration that tidied away something it did not recognise is indistinguishable from data loss. |
| **D-033** | **A retained event must be retracted when it stops being true** | Two bug reports, one cause. The hub keeps the newest instance of each coalescing event and replays the set to every client that connects, so a page paints a correct screen without waiting for the next tick — right for a level meter, wrong for progress. The last frame of a *finished* transcription pass says `running`, so every client connecting afterwards, for the life of the process, was told a pass was still going: in a mode with a `processing` state the interface sat on "Transcribing… 100%" with the record control disabled, and in `live`, which has no such state, the change was refused and the page showed "Start recording" over a clock that kept climbing. Terminal events now retract the coalescing events they end. Health events are deliberately not retracted — a level meter after a stop is stale, not wrong. Three supporting repairs came with it: the session clock freezes on the server's `ended_at` rather than on a stop the page may never have witnessed; a client that arrives after a pass ended leaves `processing` on the server's word, which is its only route back to idle; and a new session forgets the previous session's finished pass. **The past-sessions page's "0 words, 0 segments" had a separate cause and is worth recording as one**: the test suite was writing into the developer's real `data/sessions` — 949 files, 690 empty — because a `ConfigStore()` with no path resolves the real config. A suite that fills the product's own storage with garbage is a suite reporting a bug it caused. |
| **D-034** | **A recording exports as something that opens on its own** | The five existing export formats carry a transcript; none carries the video, and none can be asked a question. The sixth is a ZIP holding a folder that opens in a browser with no server, no install, and no network: the video, a transcript that follows it like captions, and a Q&A panel with the model settings built into it. Four decisions inside it are worth stating. **The transcript is the evidence and the video is addressed through it** — a local text model cannot watch a recording, so every `[MM:SS]` the model writes becomes a control that seeks the player, which is what makes a question about what was on screen answerable rather than invented. **Classic scripts, and a data bundle beside the JSON** — every browser refuses both `import` and `fetch` across `file://` URLs, and this page has to open by double-clicking it in a file manager, so `data/transcript.json` and `data/settings.json` stay the documented editable pair and win whenever they are readable while `data/bundle.js` is what makes the page work at all when they are not. **No credential is exported** — the API-key field ships present and empty and the page keeps what the user types in that browser alone, because a ZIP is exactly the sort of thing that gets forwarded. **It refuses rather than degrades** when a recording lacks video or a transcript: a "web application" with an empty player and nothing to read is not what was asked for, and shipping one under the same name disappoints quietly instead of explaining. The video-first arrangement is not a mode — closing the assistant empties a column, an empty column takes no width, so the transcript moves across and the split widens. |

| **D-035** | **Five faults in one recording, and only one of them touched the recording** | Reported together against a single window session. None had lost anything — the folder held a complete video, both transcription passes, and a muxed file with sound — and four of the five were the application *describing* that recording wrongly. **The row said "recording now" after the recording stopped**, because it asked which session was live by reading `SessionManager.store`, which since D-031 deliberately keeps answering after a session ends; the store says what can be *read*, and only `is_running` says what is being *written*. **The Audio chip said there was none**, because it tested for `audio.wav` — the file a successful pass deletes — so it read false exactly when everything had gone right, and dragged `exportable` down with it, hiding the web-app export from the only recording that qualified. **The counts were roughly doubled**, 46 segments and 479 words for a talk of 26, because the listing was the last reader still counting both passes rather than the latest (D-022); narrowing it had to be guarded on the column existing, since 25 of the 965 databases in the directory predate it and a read-only connection does not migrate. **"The transcription was never saved" was the page never asking**: `hydrate` loaded the transcript only while a session was running, so a reload after a pass — the moment the transcript is best and most wanted — showed an empty pane; the server half had been fixed under D-031 and the client half left behind. The fifth is real and structural: **the sound ran ahead of the picture**. Audio capture starts before the screen-cast portal is even asked, deliberately, so the first words of a talk are not lost while someone chooses a window from a dialog — so the video begins later, by 2.1 s here and by however long that dialog is open at worst, and a mux that lines both inputs up at zero plays them that far apart. The offset is now measured rather than assumed: nothing observes the first encoded frame arriving, so the video's start is derived as the moment it was told to stop minus its own encoded duration, and an offset that cannot be measured stays zero rather than becoming a guess. **The output keeps the audio's timeline, never the video's** — transcript timestamps are audio-relative and the exported web application syncs against that file, so trimming the audio's head to meet the video would silently invalidate every timestamp in every export. Separately, every window recording had been storing the same footage twice; the silent original now goes once the combined file is probed and holds both streams, which keeps the protection the duplication was there for and drops the duplicate. |
